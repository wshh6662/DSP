# F28384D + W5500 + HMI 项目交接文档

更新时间：2026-09-11

## 1. 当前目标

使用 TMS320F28384D 通过 SPI 控制 W5500，DSP 作为 Modbus TCP Server；威纶通 HMI 作为 Modbus TCP Client，直接读写 DSP 的寄存器与线圈。正式连接不经过电脑。

2026-09-11 起，解析层已从「只支持 FC03 / 地址 4 / 数量 2」扩展为通用 Modbus TCP 服务器，使 EasyBuilder 原工程整体切到 `MODBUS TCP/IP` 后不再出现 `PLC no response`：

- 功能码：`01` 读线圈、`03` 读保持寄存器、`05` 写单个线圈、`06` 写单个保持寄存器、`0F` 写多个线圈、`10` 写多个保持寄存器
- 通用映射：2048 个保持寄存器（协议地址 0~2047）+ 2048 个线圈（协议地址 0~2047），全部静态数组，不使用 malloc
- EasyBuilder `4x-1` 对应协议保持寄存器地址 0；`0x-1` 对应协议线圈地址 0
- 检测数量仍按 32 位发布：`4x-5`（协议地址 4）为低 16 位，`4x-6`（协议地址 5）为高 16 位，当前值 `1234` 即 `04 D2 00 00`
- 协议地址 4、5 是只读发布点：写入会被接受并回正常响应，但值不保存；读取始终返回动态检测数量（原因见第 14 节）
- `MODBUS_TCP_MAX_ADU_LENGTH` 由 64 扩到 260，支持 HMI 一次读写 120 个 word
- 格式合法但未实现的功能码回异常码 01，不再静默丢弃；连接保持不断开

## 8. 根因定位（2026-09-11）

已确认的实机现象：

- `g_w5500_version = 4`，SPI 可以读取 W5500 寄存器。
- `g_w5500_phy_link = 1`，物理链路正常。
- socket 可以从 `20` 进入 `23`，TCP 三次握手成功。
- NetAssist 能以本机 `192.168.1.30` 连接 `192.168.1.20:502`，发送正确报文后 TX 计数增加。

异常现象：

```text
g_modbus_last_receive_result = 0
g_modbus_request_count = 0
NetAssist RX = 0
```

根因在 WIZnet 库的 `socket.c`，不在 Modbus 应用层。`recv()` 的等待循环里有两个编译分支，判断顺序不一致：

```c
#ifdef IPV6_AVAILABLE
        if (recvsize != 0) { break; }                          // 先看有没有数据
        if (sock_io_mode & (1 << sn)) { return SOCK_BUSY; }
#else
        if (sock_io_mode & (1 << sn)) { return SOCK_BUSY; }    // 先判非阻塞，直接返回
        if (recvsize != 0) { break; }
#endif
```

`IPV6_AVAILABLE` 只在 `#if (_WIZCHIP_ > W5500)` 时才定义（socket.c 第 141 行）。本工程 `_WIZCHIP_` 就是 `W5500`，编译到的是 `#else` 分支；socket 0 又用 `SF_IO_NONBLOCK` 打开，因此 `recv()` 第一次循环就 `return SOCK_BUSY`，RX 缓冲区里已到达的请求永远不会被读出。

这也解释了 `g_modbus_last_receive_result = 0`：`socket.h` 第 99 行 `#define SOCK_BUSY 0`，所以 0 的含义是 `recv()` 返回"忙"，不是"没收到数据"。注意 `SOCK_ERROR` 同样等于 0，诊断变量为 0 时无法区分二者。

同一文件中生效的 `send()`（`//for speed optimization, by lihan` 版本）也忽略非阻塞模式，TX 缓冲写满时会在 `while(1)` 里死等（socket.c 第 621 行附近）。

修复内容，两处均带 `FIX 2026-09-11` 注释：

- `recv()`：把 `#else` 分支的两个判断调换顺序，与 `#ifdef IPV6_AVAILABLE` 分支及 WIZnet 官方 ioLibrary 保持一致。
- `send()`：在 `while(1)` 中加入 `if (sock_io_mode & (1 << sn)) { return SOCK_BUSY; }`，TX 满时返回忙而不是卡死主循环。此时一个字节都未发出，应用层从 `response_sent` 处重发不会产生半截报文。

验证方式：把修改后 `socket.c` 中真实的 `recv()` / `send()` 源码原样抽出，配桩函数在本机编译运行。修改前 `recv()` 返回 0 且未写 `Sn_CR_RECV`；修改后 RX 挂起 12 字节时返回 12 并写 `Sn_CR_RECV`，无数据时返回 `SOCK_BUSY` 且不阻塞，TX 空闲时 `send()` 返回 11，TX 写满（FSR = 0）时立即返回 `SOCK_BUSY`。实机验证待刷写新 `.out` 后进行。

## 12. 通用寄存器映射与功能码（2026-09-11 扩展）

映射规则：

| EasyBuilder 地址 | 协议地址 | 说明 |
|---|---|---|
| `4x-1` | 保持寄存器 0 | 通用保持寄存器，可读可写 |
| `4x-5` / `4x-6` | 保持寄存器 4 / 5 | 检测数量低字 / 高字，读动态值，禁止写入 |
| `4x-2048` | 保持寄存器 2047 | 映射上界 |
| `0x-1` | 线圈 0 | 通用线圈，可读可写 |
| `0x-2048` | 线圈 2047 | 映射上界 |

功能码支持与数量上限：

| 功能码 | 名称 | 数量上限 | 备注 |
|---|---|---|---|
| `01` | Read Coils | 2000 | 位序：每字节低位对应低地址线圈 |
| `03` | Read Holding Registers | 125 | 读到 4x-5 / 4x-6 时填入动态检测数量 |
| `05` | Write Single Coil | — | 取值仅允许 `FF00` 或 `0000` |
| `06` | Write Single Register | — | 写 4x-5 / 4x-6 正常回显但不保存 |
| `0F` | Write Multiple Coils | 1968 | 字节数字段必须等于 (数量+7)/8 |
| `10` | Write Multiple Holding Registers | 123 | 范围覆盖 4x-5 / 4x-6 时跳过这两个地址，其余照常写入 |

异常码：`01` Illegal Function（功能码未实现）、`02` Illegal Data Address（地址越界或落在受保护区间）、`03` Illegal Data Value（数量为 0、超过上限、字节数字段与数量不符、MBAP Length 与该功能码不符）。

寄存器与线圈存放在 RAM，复位后全部归零，这是当前测试阶段的预期行为。

## 14. 写操作覆盖 4x-5 / 4x-6 的处理（2026-09-11 已确定）

检测数量发布在协议地址 4、5，这两个地址是普通寄存器区中间的一个「洞」。EasyBuilder 按「地址整段间隔」成段读写，按第 4 节设置的 32，`4x-1`~`4x-32` 属于同一段，段内就夹着 `4x-5` / `4x-6`。

因此 HMI 上写一个完全无关的地址（例如 `4x-10`），发过来的请求也可能覆盖到 4、5。如果对这种请求回 `Illegal Data Address`，同一条请求里其它合法地址的写入会一起失败，HMI 侧表现为写不进去。

采用的策略是**接受写入但不保存**：

| 功能码 | 行为 |
|---|---|
| FC06 写 4x-5 / 4x-6 | 正常回显请求，值不写入 |
| FC10 范围覆盖 4x-5 / 4x-6 | 跳过这两个地址，其余地址正常写入，回正常响应 |

检测数量的保护并不依赖拒绝写入：读取路径对协议地址 4、5 根本不查 `modbus_holding_registers`，永远返回 `g_detection_count` 的低字 / 高字。所以 HMI 写进去的任何值都不会影响读值，`4x-5` 始终读到 `1234`。

副作用：HMI 若先写 `4x-5` 再读回，会读到自己没有写进去的值。这是预期行为——检测数量本来就该由 DSP 独占发布。

这一策略由 `tests/test_modbus_tcp.c` 中 `test_detection_count_ignores_writes` 覆盖：断言「跨 4x-5 / 4x-6 的整段写被接受」+「邻近地址确实写进去了」+「4x-5 / 4x-6 读值不变」。把它改回返回异常会被测试抓出。

## 15. 内存布局：modbus_data 段（2026-09-11）

通用寄存器映射落地后，`.bss` 默认落在 RAMLS5，而 RAMLS5 只有 `0x800` words，两个构建配置都链接失败：

```text
2838x_FLASH_lnk_cpu1.cmd line 77: error #10099-D: section ".bss" size 0xB0D cannot fit in RAMLS5 size 0x800
2838x_RAM_lnk_cpu1.cmd  line 74: 同样的错误
```

原因是 `modbus_holding_registers[2048]` 和 `modbus_coils[256]` 默认进 `.bss`。注意 C28x 上 `char` 也是 16 位，一个 word 就是一个 `modbus_octet_t`，所以这两个数组合计 `2048 + 256 = 0x900` words，再叠加 `.data` 的 `0x5A` 就远超 RAMLS5 的容量。

处理办法是把它们单独成段，由链接脚本放到 RAMGS0：

| 段 | 位置 | 大小 |
|---|---|---|
| `modbus_data` | RAMGS0（origin `0x00D000`，`0x1000` words） | `0x900` words = 2048 保持寄存器 + 256 线圈 |
| `.data` + `.bss` | RAMLS5（`0x800` words） | `0x5A` + `0x20D` = `0x267` words |

两个链接脚本的 SECTIONS 中都加了 `modbus_data : > RAMGS0`，**不要**加 `type=NOINIT`。段名 `ramgs0` 和 `Filter_RegsFile` 虽然也映射到 RAMGS0，但工程里没有任何代码往它们放数据，实际占用为 0。

`modbus_data` 不在 C 运行时自动清零的范围内（它不属于 `.bss`），所以 `main()` 中在 `W5500_NetworkInit()` 之前调用一次 `ModbusTcp_ResetStorage()`，用显式循环清零保持寄存器和线圈。这一步不能省，否则首次上电会读到随机值。同理没有用 `memset`：C28x 的 `char` 是 16 位，`memset` 的字节语义和 `modbus_octet_t` 数组的存储单位对不上，写出来容易看错长度。

RAMGS0 的归属在 `main()` 中显式设置为 CPU1，因为 SysConfig / `board.c` 没有配置 GS RAM 的主控（只动 GS0，RAMGS1~15、编码器、W5500 的分配都没变）：

```c
MemCfg_setGSRAMMasterSel(MEMCFG_SECT_GS0, MEMCFG_GSRAMMASTER_CPU1);
```

`MemCfg_setGSRAMMasterSel` / `MEMCFG_GSRAMMASTER_CPU1` 是 `MemCfg_setGSRAMControllerSel` / `MEMCFG_GSRAMCONTROLLER_CPU1` 的术语别名，定义在 `device/driverlib/driver_inclusive_terminology_mapping.h`，由 `device/driverlib.h` 引入。

`#pragma DATA_SECTION` 外面套了 `#ifdef __TI_COMPILER_VERSION__`：宿主的 gcc 协议测试也编译 `modbus_tcp_server.c`，不套会因为 `-Werror=unknown-pragmas` 直接编译失败。

构建后核对 map 文件：`modbus_data` 应位于 `0x00D000`、长度 `0x900`；`.bss` 应降到约 `0x20D`。

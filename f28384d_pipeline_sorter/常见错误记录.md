## 2026-09-11: W5500 非阻塞 recv() 永远返回 SOCK_BUSY，RX 缓冲区数据读不出来

- **现象**：`g_w5500_version = 4`、`g_w5500_phy_link = 1`、`g_modbus_socket_status = 23`（SOCK_ESTABLISHED），NetAssist 已连接 `192.168.1.20:502` 并发出正确的 12 字节 FC03 请求，但 NetAssist TX 增加而 RX 为 0；`g_modbus_last_receive_result = 0`、`g_modbus_request_count = 0`。
- **原因**：`socket.c` 的 `recv()` 等待循环里两个编译分支的判断顺序不一致。`IPV6_AVAILABLE` 只在 `#if (_WIZCHIP_ > W5500)` 时定义（socket.c 第 141 行），本工程 `_WIZCHIP_` 就是 `W5500`，编译到的是 `#else` 分支，而该分支先判断 `sock_io_mode`、后判断 `recvsize`。socket 0 又用 `SF_IO_NONBLOCK` 打开，于是 `recv()` 第一次循环就直接 `return SOCK_BUSY`，RX 缓冲区里的请求永远不会被读取。又因为 `socket.h` 里 `SOCK_BUSY == SOCK_ERROR == 0`，`g_modbus_last_receive_result = 0` 看起来像"没收到数据"，实际是"收到了但没读"。同一文件中生效的 `send()`（`//for speed optimization, by lihan` 版本）也忽略非阻塞模式，TX 缓冲写满时会在 `while(1)` 里死等。
- **解决办法**：在 `socket.c` 中把 `#else` 分支的两个判断调换顺序，与 WIZnet 官方 ioLibrary 一致（先判 `recvsize != 0`，再判非阻塞）；同时在 `send()` 的 `while(1)` 中加入 `if (sock_io_mode & (1 << sn)) { return SOCK_BUSY; }`，避免 TX 满时卡死 10 ms 主循环。两处均加 `FIX 2026-09-11` 注释，以后升级 ioLibrary 时注意保留。
- **验证结果**：把修改后 `socket.c` 中真实的 `recv()` / `send()` 源码原样抽出，配合桩函数在本机编译运行：RX 挂起 12 字节时 `recv()` 返回 12 并写入 `Sn_CR_RECV`；无数据时返回 `SOCK_BUSY` 且不阻塞；TX 空闲时 `send()` 返回 11；TX 写满（FSR = 0）时 `send()` 立即返回 `SOCK_BUSY` 而不是死循环。改动前的同一份源码在完全相同条件下 `recv()` 返回 0、一个字节都没读。实机 FC03 验证待刷写新 `.out` 后进行。
- **预防措施**：非阻塞 socket 上 `recv()` / `send()` 返回 0 就是 `SOCK_BUSY`（而 `SOCK_ERROR` 也是 0），不要当成"无数据/无错误"；改动 WIZnet 库后先看 `g_modbus_rx_available` 是否大于 0，再判断 `g_modbus_last_receive_result`；改完库源码必须重新编译再烧写，烧写前确认 `CPU1_FLASH` 的 `.out` 时间戳晚于 `socket.c` 的修改时间，否则烧进去的仍是旧固件、现象与修复前完全一致，很容易误判成"改了没用"。

## 2026-09-11: EasyBuilder 批量把原 MODBUS RTU 设备改为 TCP 后无法连接

## 2026-09-28: DSP 响应计数增加但 HMI 仍报告 PLC 未连接

- **现象**：DSP 收到长度11、从站1、功能码16的完整请求，`request_count` 与 `response_count` 同步增加且错误计数为0，但HMI仍提示PLC未连接。
- **原因**：启用SCI FIFO后，C2000Ware的 `SCI_isTransmitterBusy()` 只检查TX FIFO计数，不检查移位寄存器。FIFO刚空时最后一个字节仍在发送，代码立即把GPIO133切回接收，可能截断响应末尾CRC；DSP内部已经计为响应，但HMI收到的是残帧。
- **解决办法**：等待TX FIFO为空后，再延时100 us（115200 8N1一个字符约87 us），之后才把GPIO133切回接收。
- **验证结果**：新增回归测试要求发送尾延时不少于87 us；修改前测试以实际0 us失败，修改后RS485端口、Modbus RTU协议和主程序集成测试全部通过，CPU1_FLASH使用TI C2000 Compiler 22.6.2.LTS成功链接。烧录新固件后，实机连续收到FC03请求，`request_count=1495`、`response_count=1495`、响应长度29、异常码0，CRC、溢出及SCI错误均为0，确认RTU收发链路稳定；若HMI仍显示PLC未连接，应检查工程中残留的TCP设备引用。
- **预防措施**：半双工RS485切换DE/RE时不能只依据FIFO为空；必须确认移位寄存器完成，或按波特率补足最后一个字符时间，并用接收端实际校验响应CRC。

## 2026-09-11: Modbus 解析层统一要求 mbap_length == 6，FC16 写请求被静默丢弃

- **现象**：整套 HMI 迁移到 `MODBUS TCP/IP` 后显示 `PLC no response`。CCS Watch：`g_modbus_socket_status = 23`（连接正常）、`g_modbus_last_receive_result = 15`、`g_modbus_request_count = 0`、`g_modbus_last_response_length = 0`。
- **原因**：`ModbusTcp_BuildResponse()` 在入口无条件要求 `mbap_length == 6`。FC16（写多个保持寄存器）写一个寄存器的 MBAP Length 是 9（`12 34 00 00 00 09 01 10 00 0A 00 01 02 00 7B`，整帧 15 字节，正好等于 `g_modbus_last_receive_result`），长度不是 6 就被判为不合法并返回 0；主程序收到 0 后既不发送响应也不释放该帧，HMI 永远等不到应答。
- **解决办法**：把解析层重写为通用 Modbus 服务器（`ModbusTcp_ProcessRequest`）。按功能码分别校验长度，不再统一要求 6；支持 FC01/03/05/06/0F/10；合法但不支持的功能码回 `Illegal Function` 异常而不是返回 0；返回 0 只保留给 MBAP 本身无法解析的帧，且主程序改为丢弃该帧而不是留在缓冲区。同时建立 2048 保持寄存器 + 2048 线圈的通用映射，`MODBUS_TCP_MAX_ADU_LENGTH` 由 64 扩到 260，支持 HMI 一次读写 120 个 word。检测数量仍按 32 位发布在 4x-5 / 4x-6：写这两个地址会被接受并回正常响应但值不保存，读取恒返回动态值——因为 EasyBuilder 按「地址整段间隔」成段写，段内夹带 4x-5 是常态，对它回异常会让同一段内其它合法地址的写入一起失败。
- **验证结果**：宿主侧 `tests\run_modbus_tcp_tests.ps1` 共 48 处断言（44 处响应比对 + 4 处丢帧校验）全部通过。五组变异测试都能被现有测试抓出：不支持功能码静默返回 0（3 项失败）、检测数量高低字颠倒（4 项失败）、FC01 线圈位序反转（3 项失败）、FC06 写 4x-5 改回返回异常（2 项失败）、FC10 改回「整段拒绝」（2 项失败）。实机验证待刷写新 `.out` 后进行。
- **预防措施**：Modbus TCP 的长度校验必须按功能码分别做，不能用同一个 MBAP Length 卡死所有请求；任何"请求合法但返回 0 不回复"的路径都会表现为 HMI 的 `PLC no response`，排查时先看 `g_modbus_last_function` 与 `g_modbus_last_exception_code`；保护某个地址不要用"拒绝写入"，因为主站成段写时会把无关地址一起带进来，改用"接受但忽略"。

## 2026-09-11: 通用寄存器映射撑爆 RAMLS5 上的 .bss，链接失败

- **现象**：协议测试通过，但 CPU1_FLASH 和 CPU1_RAM 均链接失败：`2838x_FLASH_lnk_cpu1.cmd line 77: error #10099-D: section ".bss" size 0xB0D cannot fit in RAMLS5 size 0x800`，`2838x_RAM_lnk_cpu1.cmd` 第 74 行报同样的错。
- **原因**：`modbus_holding_registers[2048]` 与 `modbus_coils[256]` 默认进 `.bss`，而两个链接脚本都把 `.bss` 放在只有 `0x800` words 的 RAMLS5。C28x 上 `char` 也是 16 位，一个 word 就是一个 `modbus_octet_t`，两个数组合计 `0x900` words，再叠加 `.data` 的 `0x5A` 远超 RAMLS5 容量。这不是代码错误，是默认内存段容量不足。
- **解决办法**：用 `#pragma DATA_SECTION` 把两个数组放进独立段 `modbus_data`，两个链接脚本的 SECTIONS 中加入 `modbus_data : > RAMGS0`（RAMGS0 有 `0x1000` words，工程内无其它数据占用）。不加 `type=NOINIT`；由于自定义段不在 C 运行时自动清零范围内，新增 `ModbusTcp_ResetStorage()` 用显式循环清零，在 `main()` 中 `W5500_NetworkInit()` 之前调用一次。同时显式设置 `MemCfg_setGSRAMMasterSel(MEMCFG_SECT_GS0, MEMCFG_GSRAMMASTER_CPU1)`，因为 SysConfig/board.c 未配置 GS RAM 归属。
- **验证结果**：宿主测试 54 处断言（50 处响应比对 + 4 处丢帧校验）全部通过，其中新增 `test_reset_storage_clears_the_map` 验证清零函数对保持寄存器和线圈都有效；删掉该函数里的线圈清零循环后测试立即失败，证明断言有效。内存账：`modbus_data` `0x900` words 放入 RAMGS0(`0x1000`)，`.bss` 降到 `0x20D`、加 `.data` `0x5A` 合计 `0x267` words 放入 RAMLS5(`0x800`)。实机链接与烧写待 CCS 构建后确认。
- **预防措施**：C2000 工程里 `.bss` 默认落在 RAMLS 段，单段只有 `0x800` words；放大块静态数组前先估算目标段容量，必要时用 `#pragma DATA_SECTION` 单独成段放到 RAMGS。自定义段不会被 C 运行时自动清零，必须自己初始化；清零用显式循环而不是 `memset`，因为 C28x 的 `char` 是 16 位。

- **预防措施**：一次性命令线圈写入后应明确复位；HMI 按钮同时检查 OFF/ON 状态文字与操作方式，其他异常按钮逐一核对地址和触发语义。

## 2026-09-29: 报警清除和队列复位按钮写入后保持 ON

- **现象**：HMI 中报警清除等按钮按一次后出现类似计数清零的状态异常，重启 DSP 后恢复。
- **原因**：地址表将队列复位、报警清除分别列为 `0x-87` 和 `0x-88`（协议线圈地址 86、87）；DSP 通用 Modbus 写入会保持线圈 ON，仅计数清零线圈 82 原先有自动复位逻辑。
- **解决办法**：将协议地址 86、87 作为一次性命令位，在有效 ON 写入后自动恢复 OFF；检测等持续状态线圈保持原行为。当前工程未找到报警和队列业务处理模块，因此本次只修复命令位锁存，不声称已实现实际报警或队列动作。
- **验证结果**：宿主测试复现报警清除线圈写入后读回 1；修复后地址 86、87 读回 0，检测开关地址 80 仍读回 1。实机 HMI 尚待确认。
- **预防措施**：迁移 HMI 地址表时逐项区分命令位和状态位，并分别测试写入、读回、业务动作及按钮 ON/OFF 显示。
